School Hub: Profile, Admin Powers & Speed Fix Plan
Prepared for the School Hub coding agent · 26 October 2026 · apply in order
How to use this plan
• Work top to bottom. Every task has an ID, the files to touch, the exact change and an Acceptance test. A task is not done until its acceptance test passes.
• Rules ↔ client parity is the most important habit. Earlier rounds broke things by changing only one side. When you change a Firestore rule, grep the client for every write to that path and update it in the same commit. When you change a client payload, check it against the rule.
• Never write “tested” unless you ran it. After every phase run node --check on all JS, the import/export check, the getElementById check, and the Rules Playground cases in Phase D. If you could not run something (emulator, browser), say so.
• Escape every user string with escapeHtml / escapeAttr. A variable named safe… must really be escaped.
• No inline handlers, no style= attributes, keep each file under 300 lines.
• Editing firestore.rules or firestore.indexes.json does nothing until it is deployed (firebase deploy --only firestore). Pushing to GitHub only publishes the website.

Phase A: profile page and admin powers
A1 (HIGH) “You Haven’t Created Your Profile Yet” shown to people who have a profile
Root cause (reproduced by running the real updateProfile()): students.js looks for a profile only inside store.get('students'). That array holds just the first page of 30 students of the viewer’s own class. If the person is not in it, the screen calls renderProfileView(null) or { isUncreated: true }, and both render the same “create your profile” page.

Fix (files: src/features/students/students.js, students.render.js, students.modal.js):
1. Add a profile cache and a single-document fetch (rules already let any active member read students/{id}). Import getDocument from core/db/firestore.js.
const profileCache = new Map();
let profileToken = 0;
async function fetchProfile(id) {
  if (!id) return null;
  if (profileCache.has(id)) return profileCache.get(id);
  const p = await getDocument('students', id);
  if (p) profileCache.set(id, p);
  return p;
}
2. Rewrite updateProfile(studentId):
function updateProfile(studentId) {
  const user = authService.getCurrentUser();
  const wantedId = (!studentId || studentId === 'my-profile') ? user?.uid : studentId;
  if (!wantedId) { renderProfileView({ isLoading: true }); return; }
  const list = store.get('students') || [];
  const hit = list.find(s => (s.id || s.uid) === wantedId);
  if (hit) { profileCache.set(wantedId, hit); show(hit); return; }
  if (profileCache.has(wantedId)) { show(profileCache.get(wantedId)); return; }
  const token = ++profileToken;
  renderProfileView({ isLoading: true });
  fetchProfile(wantedId).then(p => {
    if (token !== profileToken) return;                  // user moved on
    if (p) show(p);
    else if (user && wantedId === user.uid) renderProfileView({ isUncreated: true }, user.uid);   // ONLY place
    else renderProfileView({ notFound: true });
  }).catch(() => { if (token === profileToken) renderProfileView({ loadFailed: true }); });
  function show(p) {
    const id = p.id || wantedId;
    store.set('currentStudentId', id, false);
    const sel = document.getElementById('profile-student-select'); if (sel) sel.value = id;
    renderProfileView(p, user ? user.uid : null);
  }
}

A6 (HIGH for cost) Moderation tab reads the whole database and can show a false “all clear”
Today: chat reports scan every message of every class; photo reports read every student; memory and superlative reports come from a store that is empty unless that screen was opened first.
Design: a reportQueue collection (one cheap query). Rules:
match /reportQueue/{id} {
  allow create: if isActive() && siteWritable() &&
    request.resource.data.keys().hasOnly(['kind','classId','targetId','targetPath','reporterUid','reason','details','createdAt']) &&
    request.resource.data.reporterUid == request.auth.uid &&
    id == request.resource.data.kind + '_' + request.resource.data.targetId + '_' + request.auth.uid &&
    request.resource.data.kind in ['chat','photo','memory','superlative','gallery'] &&
    request.resource.data.reason in ['inappropriate','harassment','spam','other'] &&
    request.resource.data.details is string && request.resource.data.details.size() <= 200 &&
    request.resource.data.targetId is string && request.resource.data.targetId.size() <= 100 &&
    request.resource.data.targetPath is string && request.resource.data.targetPath.size() <= 200 &&
    request.resource.data.classId is string && request.resource.data.classId.size() <= 30 &&
    request.resource.data.createdAt == request.time;
  allow read, delete: if isAdmin();
  allow update: if false;
}
Client: every report action becomes one writeBatch = the existing reports.<uid> update (keeps the 3-report auto-hide) + set(reportQueue/<kind>_<targetId>_<uid>).
Moderation tab: query(reportQueue, orderBy('createdAt','desc'), limit(100)), group by kind + targetId, and fetch the target document only when the admin expands the row. Actions:
• Dismiss: one batch that deletes the queue entries for that target and clears reports on the target.
• Delete content.
• Mute 24h (chat).
• Remove photo: ONE atomic batch containing the students update, delete avatars/{uid}, the users photoRemovedNotice, and the adminLog entry (today the avatar delete is outside the batch and its error is swallowed).
• Ban.
Add “Load more”. Show “No open reports” only after a successful query; show an error state if the query fails.
Acceptance: as a student report a chat message, a photo, a memory and a superlative → all four appear in the tab using one query; dismiss and delete work; turning the network off shows an error, never “all clear”.

Phase B: why the site is slow, and the fix
Measured on the code: 43 JS modules in an 8-level import chain (every level is a network round trip before anything runs), 19 render-blocking CSS files, 3 serial Firebase SDK imports, a serial boot (SDK → auth → users doc → admins doc → classes → router), and every screen loads its data twice.
B1 (HIGH) Every screen’s data loads twice and the page jumps to the top
auth.js attaches onSnapshot(users/{uid}). Its first callback fires immediately and calls setUser() again. The router re-runs switchTo() on every setUser(), which re-runs every screen’s onEnter (re-subscribe, re-fetch, syncClasses()) and scrollTo(top). The same happens on every later change of the user document.
router.js:
// in init():
this._routeSig = null;
store.subscribe('user', (u) => {
  if (!this.authReady) return;
  const sig = u ? [u.uid, u.status, u.banned, u.isAdmin, u.classId].join('|') : 'out';
  if (sig === this._routeSig) return;     // ignore echoes with the same routing data
  this._routeSig = sig;
  this.handleHashChange();
});
// in onAuthReady(): compute this._routeSig from the current store.get('user') BEFORE the first switchTo
// in switchTo(): scroll only when the screen really changed
if (prevScreenId !== screenId) window.scrollTo({ top: 0, behavior: 'smooth' });
Acceptance: open the class screen: the Network tab shows each Firestore query once; changing mutedUntil in the console does not reload the screen.

• config/firebase.js: const [{ initializeApp }, { getAuth }, { getFirestore }] = await Promise.all([import('…firebase-app.js'), import('…firebase-auth.js'), import('…firebase-firestore.js')]);
• auth.js _loadProfile: const [userSnap, adminSnap] = await Promise.all([getDoc(userRef), getDoc(adminRef).catch(() => null)]); (create the user document afterwards if it is missing).
